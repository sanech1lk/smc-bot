# BudChat

Мобильный PWA-мессенджер для строительных бригад. Чат, фото, задачи и смета
привязаны не к дате, а к **объекту стройки** и его **этапу** (Подготовка →
Демонтаж → Электрика → Сантехника → Штукатурка → Стяжка → Плитка → Ламинат →
Покраска → Сдача).

Стек: Next.js 14 (App Router) + TypeScript + Tailwind CSS + PostgreSQL (Prisma) +
NextAuth.js + Socket.io.

## Чем отличается от Fieldwire / CompanyCam / Buildertrend / АИ-Прораб

- **GPS + таймстамп прямо в фото.** Каждое фото штампуется на устройстве
  (дата, время, координаты) перед загрузкой — как у CompanyCam, но входит в
  базовый функционал без отдельной подписки.
- **План объекта с метками.** Загрузили чертёж/план — ставите метки прямо на
  нём (проблема, привязка к этапу), а не только в общей галерее, как у
  Fieldwire.
- **Push-уведомления** о новых сообщениях и назначенных задачах даже при
  закрытом приложении (Web Push, без нативного клиента).
- **Голосовой ввод** сообщений и названий задач — работа в перчатках не мешает
  писать.
- **Кастомные этапы** — стартовый список из 10 этапов ремонта можно менять
  под любой тип объекта прямо при создании или позже.
- **Офлайн-очередь** — сообщения и фото, отправленные без связи на объекте,
  сохраняются на устройстве и уходят сами при появлении сети.
- **PDF-смета** одной кнопкой — для отправки заказчику.
- **Мультивалютность** — рубль, евро, злотый, доллар, тенге, гривна, фунт,
  крона: валюта задаётся на уровне объекта и применяется к сметам и PDF.
- **Шаблоны смет** по типу работ (демонтаж, электрика, санузел и т.д.) —
  прораб не вбивает позиции с нуля.
- **QR-код объекта** — рабочий сканирует его на площадке и попадает в объект
  без ввода email; приглашённые по почте вступают автоматически при регистрации.
- **Сводка по всем объектам** — проблемные этапы, просроченные задачи и
  ближайшие выезды одним экраном.
- **Светлая и тёмная тема** с автоподстройкой под систему.

### Полевые модули (то, за чем обычно уходят к Procore/Raken)

- **Допработы с подписью.** Заказчик согласовывает изменение сметы пальцем
  прямо в приложении. Подписанное решение нельзя переиграть или удалить —
  это снимает спор «мы такого не заказывали» на сдаче.
- **Учёт смен.** Рабочий открывает и закрывает смену, место фиксируется по
  GPS. Прораб видит табель по бригаде, рабочий — только свои часы.
- **Ежедневный отчёт.** Погода, сколько человек вышло, что сделано, какие
  были проблемы — один структурированный документ в день (как в Raken),
  который можно показать заказчику вместо ленты чата.
- **Разметка на фото.** Обвести скол или поставить стрелку прямо на снимке.
  Штрихи хранятся отдельно от файла, поэтому оригинал с GPS-штампом
  остаётся нетронутым.
- **Список дефектов (punch list).** Замечание → в работе → устранено →
  принято. Перевести в «принято» может только заказчик или админ.
- **Учёт материалов.** План против факта, перерасход подсвечивается красным.
- **Портал заказчика.** Отдельный экран: готовность в процентах, смета плюс
  согласованные допы, свежие фото, ближайший выезд и всё, что ждёт его
  подписи. Табели и себестоимость материалов заказчику не показываются.

## Быстрый старт (Docker)

```bash
cp .env.example .env
docker compose up --build
```

Приложение поднимется на `http://localhost:3000`, база данных — в контейнере
`postgres`. Миграции применяются автоматически при старте контейнера `app`.

Чтобы заполнить демо-данными (три пользователя, объект, этапы, задача, смета,
чек-лист):

```bash
docker compose exec app npx tsx prisma/seed.ts
```

## Локальная разработка

```bash
npm install
cp .env.example .env          # укажите DATABASE_URL своей PostgreSQL
docker compose up -d postgres # либо своя локальная PostgreSQL
npx prisma migrate dev
npm run prisma:seed
npm run dev
```

`npm run dev` запускает `server.js` — кастомный Node-сервер, оборачивающий
Next.js и поднимающий Socket.io на том же порту (`/socket.io`) для чата и
живых обновлений фото/задач/сметы/чек-листа.

## Роли и права

- **ADMIN** (прораб) — полный доступ: участники, этапы, задачи, смета.
- **WORKER** (мастер/рабочий) — чат, фото, задачи, смета, статус этапов.
- **CLIENT** (заказчик) — чтение, отметка пунктов чек-листа, подпись приёмки
  пальцем, перевод задачи из статуса «На проверке» в «Готово».

## Цветовая индикация этапов

Серый — не начато, жёлтый — в работе, зелёный — готово, красный — проблема.
Подпись заказчика на чек-листе приёмки автоматически переводит этап в статус
«Готово».

## Почта (SMTP)

Восстановление пароля и приглашения участников отправляются по email.
Если SMTP не настроен (см. `.env.example`), письма **не отправляются**, а их
текст печатается в консоль сервера — этого достаточно, чтобы проверить оба
сценария локально.

## Тесты

```bash
npm test
```

Покрыты чистые модули, где ошибка стоила бы дорого: rate limiter, генерация и
хеширование токенов, форматирование валют, консистентность шаблонов смет,
часы смен и перерасход материалов, очистка отчётов об ошибках от персональных
данных. Последний случай проверяется дважды: юнит-тестами самого фильтра и
сквозным тестом, который поднимает локальный приёмник, инициализирует
настоящий Sentry SDK и проверяет байты, реально ушедшие из процесса.

## Логи и ошибки

### Где смотреть логи

```bash
docker compose logs -f app          # живой лог приложения
docker compose logs --tail 200 app  # последние 200 строк
docker compose logs --since 30m app # за последние 30 минут
docker compose logs postgres        # лог базы данных
```

В Docker Desktop то же самое мышкой: **Containers** → контейнер `app` →
вкладка **Logs**. На Railway — **Deployments** → активный деплой, где
**Build Logs** это сборка образа, а **Deploy Logs** — работающее приложение.

Признак нормального старта — строка `> BudChat ready on http://0.0.0.0:3000`
после накатывания миграций. Если её нет, причина будет прямо над этим местом.

### Отчёты об ошибках (Sentry)

Логи живут до перезапуска контейнера и не содержат ошибок, случившихся в
браузере у пользователя. Sentry закрывает обе дыры: хранит историю и ловит
сбои на устройстве.

Включается одной переменной — заведите бесплатный проект на sentry.io, тип
Next.js, скопируйте DSN и положите в `.env`:

```
SENTRY_DSN="https://xxxx@oNNN.ingest.sentry.io/NNN"
```

Дальше `docker compose up --build` (пересборка нужна: браузерная часть
вшивается в бандл на этапе сборки, серверная читается при старте). Пока
переменная пустая, SDK вообще не инициализируется — приложение работает
идентично.

Что уходит в отчёт: текст ошибки, место в коде, адрес страницы **без**
параметров запроса, тип браузера и id пользователя.

Что вырезается перед отправкой (`src/lib/sentry-scrub.ts`): тело запроса,
cookies, строка запроса целиком (там ездит токен сброса пароля), все
заголовки кроме `user-agent`, email, телефон, имя, адрес, GPS-координаты,
подписи, IP-адрес и имя сервера. Запись экрана (session replay) и захват
локальных переменных выключены намеренно — на объекте они попали бы в
отчёт вместе с данными заказчика.

Замеры производительности по умолчанию выключены: они расходуют бесплатный
лимит намного быстрее ошибок. Включаются через
`NEXT_PUBLIC_SENTRY_TRACES_SAMPLE_RATE` (например `0.1` — десятая часть
запросов).

Отчёты идут через собственный домен (`/monitoring`), поэтому блокировщики
рекламы их не режут.

## Push-уведомления

Работают только если заданы `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` (см.
`.env.example`) — без них приложение просто не покажет переключатель 🔔.
Сгенерировать пару:

```bash
npx web-push generate-vapid-keys
```

**Важно:** и push, и геолокация для GPS-штампа на фото требуют secure context
— на `localhost` работает без HTTPS, но в проде домен должен быть на HTTPS.

## PWA

`public/icons/` содержит и векторную (`icon.svg`), и растровые иконки
(`icon-32.png`, `icon-192.png`, `icon-512.png`, `icon-512-maskable.png`) —
последние нужны для установки как приложения и обязательны для публикации
в Google Play через TWA. Если захотите свой брендинг — перегенерируйте эти
файлы из нового `icon.svg`/`icon-maskable.svg` (любой SVG→PNG рендерер) и
не меняйте имена файлов, они уже прописаны в `manifest.json`.

## Публикация в Google Play (TWA)

Google Play не принимает голый PWA — нужна тонкая нативная обёртка
**TWA (Trusted Web Activity)**, которая открывает уже задеплоенный сайт.
Всё ниже имеет смысл только после того, как приложение развёрнуто на
боевом домене с HTTPS (см. `docker-compose.yml` — этот же образ годится
для любого Docker-хостинга).

**Понадобится на компьютере, откуда собираете:** Node.js, JDK 17+
(Bubblewrap сам предложит поставить Android SDK при первом запуске).

```bash
npm install -g @bubblewrap/cli

# Инициализация — Bubblewrap сам прочитает manifest.json с вашего домена
# и предложит пакет вида dev.budchat.twa (можно оставить)
bubblewrap init --manifest="https://ВАШ_ДОМЕН/manifest.json"

# На вопросах установите:
#   Application ID: dev.budchat.twa (или свой — тогда поправьте
#     public/.well-known/assetlinks.json под свой package_name)
#   Signing key: дайте Bubblewrap создать новый keystore и ЗАПОМНИТЕ пароли —
#     без этого файла вы не сможете выпускать обновления приложения

bubblewrap build
```

Дальше — обязательный шаг верификации домена (без него в приложении будет
видна адресная строка браузера):

```bash
keytool -list -v -keystore android.keystore -alias android
```

Скопируйте `SHA256` из вывода и вставьте в
`public/.well-known/assetlinks.json` вместо
`REPLACE_WITH_SHA256_FROM_YOUR_ANDROID_KEYSTORE`, задеплойте изменение —
файл должен отдаваться по адресу `https://ВАШ_ДОМЕН/.well-known/assetlinks.json`.

Готовый `app-release-signed.aab` из `bubblewrap build` загружается в
[Google Play Console](https://play.google.com/console) (аккаунт — разово
$25). Там же: скриншоты, описание, ссылка на политику конфиденциальности
(обязательна), анкета Data Safety.
